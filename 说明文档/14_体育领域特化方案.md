# 体育领域特化方案 v0.1（供评审）

> 对象：`店子宠物/` 这套「AI 商家营销运营助手」（FastAPI + SQLite + 单页前端，79 条测试全绿）
> 目标：先把「这套网页现在能干什么」讲清楚 → 提出**体育领域**中它能大致解决的问题 → 给出把它**改造成体育特化版**的实现方案
> 本文只做设计，不改代码。确认方向后再按 P0/P1 落地。

---

## 0. 一页结论

| 问题 | 一句话回答 |
|---|---|
| 这套网页的本质是什么 | 一个**商品知识库 + 平台规则库 + 利润计算引擎 + 热点匹配器 + 内容生成器**的编排层（AI 只负责理解/判断/生成，数字与规则由程序保证） |
| 它现在解决的是谁的问题 | 中小商家（现在这套 demo 是遥控模型店）：**卖什么价不亏、蹭什么热点能带量、发什么内容能过审** |
| 体育领域能用吗 | 能，而且是**改造成本最低**的领域之一：热点管线里已经有「B站运动分区（rid 234）+ 运动健身分类词表」，缺的只是「运动语义 + 赛事日历 + 装备成本口径」 |
| 最主要的缺口在哪 | 通用电商口径会**高估体育用品利润**：体育用品是重货（按重量计费运费）、多尺码（退货率高）、强赛事季（促销有明确时间窗），这三件事现有引擎都没算 |
| 建议的落地形态 | 方向 A：**运动装备零售店的 AI 营销 + 利润防护台**（保留五大模块骨架，替换领域知识层，扩展利润引擎与赛事雷达） |
| 工作量 | P0（可演示）≈ 12 个改动点；P1（好用）≈ 8 个改动点；P2（可选）不做也不影响演示 |

## 1. 先看清楚：这套网页现在能干什么

### 1.1 五个页面 = 五个能力模块

| 页面 | 输入 | 它做了什么 | 输出 |
|---|---|---|---|
| **商品管理** | 一段原始资料（大白话）、或 Excel 表格 | ① 结构化提取（名称/品牌/品类/规格/卖点/人群/合规限制/自动标签）；② 表格批量导入（自动找表头、列语义、合并单元格、预览后确认入库）；③ 单件利润与**推荐售价**（按成本 + 佣金 + 运费 + 期望毛利率反算保本价与建议区间） | 结构化商品档案 + 单件利润 + 建议售价 |
| **利润防护** | 一句促销计划（"两件八折再发 29 元券"）或表单 | ① 对话式 Agent 调工具算账（数字只能来自引擎）；② 逐项拆解账单；③ **优惠逐项归因**（不促销 / 只发券 / 只打折 / 叠加 四行对比）；④ 全店体检（同一套活动铺全店）；⑤ 跌破毛利率红线拦截；⑥ 给可选调整方案 | 账单 + 归因 + 风险判定 + 建议 |
| **内容生成** | 商品 + 平台 + 内容类型 | ① 按平台硬限制生成（标题字数、标签数、emoji 开关、禁用词）；② 短视频直接出分镜；③ **事实校验**（正文里的数字必须能追溯到商品档案）；④ 人工审核状态机（draft→pending→approved/rejected） | 5 个平台的文案 / 脚本 / 详情页 |
| **热点看板** | 自动采集（头条/B站/B站分区/知乎日报） | ① 打板块标签（游戏/食品/数码/汽车/宠物/家居/**运动健身**/户外/健康…）；② 两阶段匹配：程序算 R/T/A 分 → 大模型判 P/C 分与风险 → 汇总 `S = 0.30R + 0.25T + 0.20A + 0.15P + 0.10C`；③ 每张机会卡给关联逻辑、创意、内容形式、风险、发布前检查 | 热点 × 商品 的「机会卡」，可审核 |
| **设置** | 商家确认口径 | ① 大模型接入（DeepSeek / ChatGPT / 通义千问，也可不填 Key 走内置 Mock）；② **计价口径可编辑**（佣金率、佣金基数、运费、满件折扣、毛利率红线、默认券额） | 全店铺的"口径真相源" |

### 1.2 四个可复用的底座（这才是特化时真正要动的地方）

```
config/
├── platforms.yaml            # 5 个平台的硬限制（字数/标签/emoji/禁用词/结构）+ 算法要点
├── platform_skill_*.md       # 5 份平台写作方法（注入提示词）
├── pricing_policy.yaml       # 促销利润口径：佣金率、佣金基数、运费、满件折扣、毛利率红线、追问话术、越权拦截
├── sources.yaml              # 热点源开关 + 板块分类词表 + 来源分类映射
├── risk_keywords.yaml        # 敏感/负面词
└── agent_skill.md            # 利润顾问 Agent 的行为规范（铁律/工具/对话协议/边界）

app/
├── models.py                 # products / hotspots / contents / matches / promo_configs / profit_checks / agent_sessions / product_costs
├── services/
│   ├── extraction.py         # 原始资料 → 结构化商品（含自动标签：品类/功能/场景/人群/痛点/价格带/可蹭热点类型）
│   ├── table_parser.py       # Excel → 商品（表头识别、列语义、合并单元格）
│   ├── pricing.py            # 纯函数计价引擎（每个数字可追溯）
│   ├── agent.py              # 对话 Agent（工具：list_products / calc_profit / store_scan / get_policy / get_cost）
│   ├── matching.py           # 两阶段热点×商品匹配（W = r.30 t.25 a.20 p.15 c.10）
│   ├── content.py            # 平台内容生成 + 事实校验 + 审核
│   ├── hotspots.py           # 采集调度 + 板块打标
│   └── collectors/           # 头条 / B站 / B站分区 / 知乎日报
```

**关键设计原则（决定改造方式）**：
1. **AI 不产生数字**——金额、佣金、利润率全部来自 `pricing.py` 纯函数，模型只负责表达；
2. **规则外置**——换平台/换店铺只改 YAML，不改代码；本方案的体育化也优先落在这层；
3. **只新增表、不改老表字段**（`create_all()` 不迁移），所以体育属性要放**新表**；
4. **留痕**——每次测算写 `profit_checks`，每个机会卡存 subscores，便于追溯。

## 2. 体育领域：这套网页能大致解决的问题

> 说明：下面每个问题都标注「用哪些模块」「现在能到什么程度」「还缺什么」。
> 标记 ✅ 现在就能跑、🟡 改配置/小改即可、🔴 需要开发（就是本次特化要做的事）。

### 2.1 角色 A：运动装备 / 体育用品店主（最贴合）

| # | 具体问题 | 用哪些功能 | 现在能到什么程度 |
|---|---|---|---|
| A1 | 「下周北马开赛，我店里有 12 款跑鞋、压缩裤、能量胶，这周该主推哪几款、配什么内容？」 | 热点看板（赛事热点 → 匹配）→ 内容生成 | 🟡 匹配能跑，但热点里没有"赛事日历"概念，只能等新闻上榜；缺"赛前 30 天备战期"的提前量 |
| A2 | 「碳板跑鞋进价 899 标价 1299，做满 2 件 85 折 + 50 元券，还赚钱吗？」 | 利润防护（对话 → calc_profit → 账单 → 归因） | ✅ **现在就能算**，只要把这款商品和成本录进去 |
| A3 | 「羽毛球拍发货 2.3 kg，现在按固定运费 15 元算，是不是高估利润了？」 | 利润防护 | 🔴 引擎只有「固定运费」口径，没有**首重/续重**；体育重货会系统性算高利润 |
| A4 | 「足球鞋尺码退货率 30%，促销要不要把退货成本算进去？」 | 利润防护 | 🔴 现在明确不计退货率（通用版是诚实做法：新店没数据），但体育多尺码品类这条是硬损失 |
| A5 | 「同款跑鞋在天猫/抖音/得物佣金和活动都不一样，怎么定价不打架？」 | 设置（PromoConfig 多套口径） | 🟡 表结构支持多套口径（`platform` 字段），但没有"多平台对比算账"的入口 |
| A6 | 「一批滑雪护具压货，雪季前怎么出清不亏？」 | 热点看板（季节）+ 利润防护（清仓定价）+ 内容生成（清仓话术） | 🟡 逻辑通，缺"雪季/泳季/马拉松季"的季节日历 |
| A7 | 「小红书发训练打卡，怎么保证不写『治好膝盖疼』这种违规功效词？」 | 内容生成（禁用词 + 事实校验） | ✅ 有禁用词表与数字校验；🟡 缺体育专属红线（疗效宣称、运动员肖像、赛事画面版权） |
| A8 | 「Excel 里 200 个 SKU（尺码 × 颜色）要建档并批量算利润」 | 表格批量导入 + 批量运算 | ✅ 能跑；🟡 缺「尺码矩阵」概念，同款不同码会被当成不同商品 |
| A9 | 「一款瑜伽垫要在 5 个平台发，标题字数和标签限制能不能自动满足？」 | 内容生成（平台硬限制） | ✅ 能跑（小红书标题 ≤20 字、标签 ≤10；抖音 ≤55 字、≤5 标签；B站 ≤40；快手 ≤45；电商 ≤60） |
| A10 | 「新手跑者和进阶跑者话术不一样，怎么自动分开写？」 | 商品人群字段 + 内容生成 | 🟡 有人群字段，缺体育专属人群画像（新手跑者/进阶/精英/青少年/中老年健走） |

### 2.2 角色 B：健身教练 / 健身房 / 训练营

| # | 具体问题 | 用哪些功能 | 现在能到什么程度 |
|---|---|---|---|
| B1 | 「双11 年卡送 3 节私教，这个套餐会不会亏？」 | 利润防护 | 🟡 能把"私教课"当虚拟商品建条目录成本和售价来算；🔴 缺服务类成本模型（课时人力成本、赠品成本、有效期履约风险） |

| C2 | 「青训招生季用『体测达标』做内容，怎么不踩『包过/承诺提分』的红线？」 | 内容生成（禁用词 + 事实校验） | 🟡 通用禁用词能拦一部分，缺教育/体育培训专属红线 |
| C3 | 「『苏超』『村BA』这种地域性体育热点，我们这种小店能蹭吗？」 | 热点看板（匹配 + 风险） | ✅ 匹配能判断"关联弱就不建议硬蹭"，这正是它的设计初衷 |

### 2.4 角色 D：体育垂类内容创作者 / 品牌方

| # | 具体问题 | 用哪些功能 | 现在能到什么程度 |
|---|---|---|---|
| D1 | 「体育垂类账号，怎么判断一个热点值不值得蹭？」 | 热点看板 | ✅ 现成能力（机会卡带关联逻辑 + 风险 + 检查清单） |
| D2 | 「品牌方要控价，经销商在抖音低价倾销怎么发现？」 | — | 🔴 **不在能力范围**（没有价格监控/爬虫能力），明确划掉，别硬吹 |

### 2.5 小结：三类问题的可解决度

```
✅ 直接能解决（不用改代码）：促销利润测算、违规词拦截、多平台文案、热点×商品匹配、Excel 批量建档
🟡 改配置/小改能解决：体育品类树、赛事/季节日历、体育人群画像、平台差异口径
🔴 必须开发：重量运费、退货期望损失、赛事雷达、体育属性模型、体育合规规则
```

## 3. 特化方向选择

| 方向 | 定位 | 改动量 | 建议 |
|---|---|---|---|
| **A. 运动装备零售台**（推荐） | 一家卖跑鞋/骑行/球类装备的店，用这套系统决定"定多少价、蹭哪个赛事、发什么内容" | 中（复用 80%） | ✅ 现有引擎就是商家口径，改造最顺；演示效果最稳 |
| B. 健身房/训练营运营台 | 卖课、卖卡、做活动 | 大（要加服务类成本模型、履约、有效期） | 暂不建议，会偏离现有引擎的能力边界 |
| C. 赛事/俱乐部内容台 | 做赛事应援、赞助商内容 | 中（要加赛事日历、内容节奏） | 可作为 A 的 P1 子模块，独立成一版收益不大 |

**推荐 A，理由是三条硬理由**：
1. **数据现成**：`sources.yaml` 已经采集 B站运动分区（rid 234）与「运动健身」板块，`category_keywords` 里已有跑步/骑行/马拉松/篮球/足球/羽毛球/游泳/健身等词；
2. **差异可量化**：体育用品的成本结构和通用快消不一样（重货、尺码退货、赛事窗口），通用口径会算错账——这正好能做出"体育版比通用版更准"的对比演示；
3. **演示节奏强**：体育有明确的日历（赛事、赛季、开学季），"提前 30 天备战"这种叙事比"追热点"更像真业务。

### 4.2 数据模型：新增 `SportProfile`（不改老表）

> 为什么用新表：`database.py` 用 `create_all()`，**只建新表、不会给已有表加列**，老库加列会报 `no such column`。现有 `product_costs` 就是按这个原则加的，本方案沿用。

```python
class SportProfile(Base):
    __tablename__ = "sport_profiles"

    id = Column(Integer, primary_key=True)
    product_id = Column(Integer, index=True, nullable=False, unique=True)

    sport = Column(String(50), default="")          # 跑步 / 骑行 / 球类 / 力量训练 / 户外 / 水上
    sub_category = Column(String(50), default="")   # 跑鞋 / 骑行服 / 羽毛球拍
    level = Column(String(20), default="")          # 入门 / 新手 / 进阶 / 精英 / 专业
    season = Column(JSON, default=list)             # ["春秋"]
    personas = Column(JSON, default=list)           # ["进阶跑者"]

    size_system = Column(JSON, default=list)        # ["EU","US"]
    size_range = Column(JSON, default=dict)         # {"EU": ["40","41","42"], "颜色": ["黑","白"]}
    weight_g = Column(Float, nullable=True)         # 单件净重
    package_weight_g = Column(Float, nullable=True) # 发货重量（含包装）← 算运费就用这个
    package_dims_cm = Column(JSON, default=dict)    # {"长": 32, "宽": 12, "高": 8} 用于体积重

    certifications = Column(JSON, default=list)     # ["CE","EN1078"]
    return_rate = Column(Float, nullable=True)      # 该品类退货率（可覆盖 taxonomy 默认值）
    use_cases = Column(JSON, default=list)          # ["路跑","操场","跑步机"]
    note = Column(String(300), default="")
    updated_at = Column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)
```

同时给 `Product.tags` 增加两个维度（JSON 字段，不需要改表）：
`"运动项目"`、`"运动水平"` —— 这样匹配的标签命中逻辑（`_tag_terms`）自动就能用上。

### 4.3 匹配算法：从「蹭热点」升级为「踩节奏」

#### 4.3.1 两处结构性改动

1. **赛事/赛季成为第一类候选源**：`run_matching` 取候选时，除了数据库里的 Hotspot，再从 `sports_calendar.yaml` 合成"虚拟热点"（type=`event`/`season`），这样**不用等新闻上榜**就能提前 30 天出机会卡。
2. **新增 E 分（Event fit，赛事/季节契合度 0~100）**：
   - 商品项目 == 赛事项目：+60
   - 商品品类 ∈ 赛事关联品类：+20
   - 人群有交集：+10
   - 当前日期落在赛前 `prepare_window_days` 内：+10
   - 与赛季匹配（雪季×滑雪服）：70 分起
   - 无任何关联：≤20

#### 4.3.2 权重调整建议

| 分项 | 原权重 | 建议权重 | 理由 |
|---|---|---|---|
| R 关联强度 | 0.30 | 0.28 | 保持不变级 |
| T 时效 | 0.25 | 0.22 | 赛事有窗口期，时效仍重要 |
| A 人群 | 0.20 | 0.16 | 体育人群标签更细，但不需要最高权重 |
| P 营销潜力 | 0.15 | 0.14 | — |
| C 可信度 | 0.10 | 0.10 | — |
| **E 赛事/季节契合** | — | **0.10** | 新增，专门表达"这件事和我的运动项目有没有关系" |

`S = 0.28R + 0.22T + 0.16A + 0.14P + 0.10C + 0.10E`

#### 4.3.3 新增硬门槛（比调权重更有效）

```
if E < 40 and R < 60: 直接丢弃（不做机会卡）
if 商品涉及儿童且热点含赛事暴力/受伤画面: 直接丢弃
if 热点为敏感事件（沿用 risk_keywords.yaml）: 直接丢弃
```

**诚实说明**：权重重排本身只会让分数动 1~3 分，真正起作用的是 ① 赛事日历带来的"提前量"、② E 分的硬门槛、③ 品类树距离让"同项目"的关联被正确识别。这三点才是特化的实质。

#### 4.3.4 示例（同一个热点，新旧得分对比）

案例：跑鞋 ×「北京马拉松开赛」预热热点
`R=88 T=92 A=82 P=78 C=86 E=95`

```
新：0.28×88 + 0.22×92 + 0.16×82 + 0.14×78 + 0.10×86 + 0.10×95
  = 24.64 + 20.24 + 13.12 + 10.92 + 8.60 + 9.50 = 87.0
旧：0.30×88 + 0.25×92 + 0.20×82 + 0.15×78 + 0.10×86 = 86.1
```

分数接近是正常的；差别在**这张卡会不会在 10 月就出现**（旧版要等热点上榜，新版赛前 30 天就出），以及**没有赛事关联的热点会被 E 分压下去**。

### 4.4 利润防护：体育化最硬的一块（这里最能体现"比通用版更准"）

#### 4.4.1 三个新增计算能力

**① 重量阶梯运费（替代固定运费）**

```yaml
# config/sports_shipping.yaml
rules:
  default:
    first_weight_kg: 1.0
    first_price: 12.0
    step_weight_kg: 0.5
    step_price: 8.0
    volumetric_divisor: 6000     # 体积重(kg) = 长×宽×高(cm) / 6000
  bulky:                          # 雪具/自行车等大件
    first_weight_kg: 5.0
    first_price: 35.0
    step_weight_kg: 1.0
    step_price: 12.0
```

```
计费重量 = max(发货重量, 体积重)
运费 = 首重价 + ceil((计费重量 − 首重) / 续重单位) × 续重价
```

**② 退货期望损失（多尺码品类）**

```
退货期望损失 = 退货率 × (发货运费 + 退回运费) + 退货率 × 折损率 × 进货成本
期望毛利 = 毛利 − 退货期望损失
```

（退货率来源：`SportProfile.return_rate` > `sports_taxonomy.yaml` 品类默认值 > 全局 0）

**③ 组合装拆解（拍+球+包、护具三件套）**

```
组合装售价 vs Σ(单品成本) + 组合包装成本 + 组合发货重量运费
→ 判断"组合装是让利还是真亏"
```

#### 4.4.2 具体演示算例（羽毛球拍，可直接对数字验收）

**商品**：威克多 挑战者 9500，标价 399，进价 268，发货重量 2.3 kg
**活动**：满 2 件 85 折 + 50 元券；佣金 6%（券后含买家运费）；买家付运费 12 元；毛利率红线 8%

| 步骤 | 计算 | 结果 |
|---|---|---|
| 成交额（商品） | 399 × 2 × 0.85 − 50 | **628.30** |
| 商品成本 | 268 × 2 | 536.00 |
| 佣金基数（券后含买家运费） | 628.30 + 12.00 | 640.30 |
| 平台佣金 | 640.30 × 6% | 38.42 |
| **通用版**：国内运费（固定） | — | 15.00 |
| **通用版利润** | 628.30 + 12 − 536 − 15 − 38.42 | **50.88** |
| **通用版毛利率** | 50.88 / 628.30 | **8.10%**（压线过关，看起来没问题） |
| **体育版**：国内运费（2.3 kg 计费） | 12 + ceil((2.3−1)/0.5)×8 = 12 + 3×8 | **36.00** |
| **体育版利润** | 628.30 + 12 − 536 − 36 − 38.42 | **29.88** |
| **体育版毛利率** | 29.88 / 628.30 | **4.76%** ← **跌破 8% 红线** |
| 若券加到 60 元 | 成交额 618.30，佣金 37.82，利润 20.48 | 毛利率 **3.31%** |

**这张表就是特化的价值证明**：通用口径说"能过线"，体育口径说"你在亏"。演示时这一屏最有说服力。

## 6. 验收与演示脚本

### 场景 1：赛事雷达 → 匹配 → 内容（3 分钟）
1. 打开「赛事雷达」：显示北马 12 天后，标签"备战期"；
2. 点「扫一遍我的商品」：碳板跑鞋 87.0 分、压缩裤 81.4 分，瑜伽垫 42 分（E 分低，被门槛挡掉）；
3. 点碳板跑鞋那张卡 →「生成小红书文案」→ 出"赛前 4 周装备清单"，标题 18 字（≤20）、标签 8 个（≤10）、无违规词；
4. 演示拦截：手动要求加"治好膝盖疼"，事实校验/合规直接拒绝并给出理由。

### 场景 2：体育口径 vs 通用口径（2 分钟）
1. 利润防护输入"羽毛球拍两件 85 折 + 50 券"；
2. 账单出 `628.30 / 536.00 / 38.42 / 运费 36.00 / 利润 29.88 / 毛利率 4.76%`，红字"跌破 8% 红线"；
3. 切到"固定运费口径"重算 → 利润 50.88 / 8.10%，对比一目了然；
4. 点"改参数重算"，把券降到 30 → 利润回升到 X（现场算并要求 >8%）。

### 场景 3：合规与事实校验（1 分钟）
1. 给足球鞋生成抖音文案；
2. 系统自动带"儿童须在成人监护下使用"（若适用）与认证信息；
3. 尝试写"比市面同类快 30%"→ 事实校验标红：数字无来源。

## 7. 风险与边界（先说清楚，避免过度承诺）

| 风险 | 应对 |
|---|---|
| 赛事日期/参赛信息可能变 | 日历文件里标 `source` 与 `updated_at`，界面上显示"以官方为准"；不抓取不实传闻 |

## 9. 特化后到底解决什么问题、靠什么解决

### 9.0 先明确：特化改的是四层，不是换皮肤

```
L1 知识层  config/*.yaml            ← 塞进"体育的常识"（品类树、赛事日历、合规词、人群）
L2 数据层  sport_profiles（新表）    ← 塞进"体育的数据"（重量、尺码、认证、退货率）
L3 算法层  pricing.py / matching.py ← 塞进"体育的算法"（重量运费、退货损失、E 分、硬门槛）
L4 交互层  index.html / agent_skill.md ← 塞进"体育的表达"（赛事雷达、账单口径切换、话术）

原有骨架（纯函数算账引擎、两阶段匹配、内容事实校验、审核状态机）100% 复用。
所以特化 = 在四个插槽里装体育零件，不是重写系统。
```

### 9.1 问题一：这个促销到底亏不亏（最刚的需求）

| 环节 | 内容 |
|---|---|
| **原来的坑** | 体育用品是**重货**（羽毛球拍发货 2.3 kg、雪具十几 kg）和**多尺码**（足球鞋退货率 30%）。通用口径按"固定运费 15 元、不计退货"算，会**系统性高估利润**——商家以为在赚钱，其实在亏 |
| **怎么解（数据）** | `SportProfile.package_weight_g`（发货重量）、`package_dims_cm`（体积）、`return_rate`（该品类退货率） |
| **怎么解（规则）** | `sports_shipping.yaml`：首重 1 kg / 12 元，续重 0.5 kg / 8 元，体积重除数 6000；大件单独一档 |
| **怎么解（算法）** | ① `计费重量 = max(发货重量, 体积重)`；② `运费 = 首重价 + ceil((计费重量−首重)/续重单位) × 续重价`；③ `退货期望损失 = 退货率 × (发货运费 + 退回运费) + 退货率 × 折损率 × 进货成本`；④ `期望毛利 = 毛利 − 退货期望损失` |
| **怎么解（表达）** | 账单里运费行显示"按 2.3 kg 计费 **36.00**（固定口径为 15.00）"，并给一个**口径切换开关**；差额直接摊在商家眼前 |
| **可验证结果** | 同一次测算：通用口径利润 **50.88 / 毛利率 8.10%**（压线"能过"）→ 体育口径 **29.88 / 4.76%**（跌破 8% 红线） |

一句话：**把"看不见的成本"变成账单上一行能对账的数字。**

### 9.2 问题二：这个赛事该不该蹭、什么时候开始蹭

| 环节 | 内容 |
|---|---|
| **原来的坑** | 旧版只能等热点**上榜**才知道（赛前 1 天全网都是北马，你的内容已经排不上队）；体育热点有强日历性，运营要的是**提前 30 天的备战期** |
| **怎么解（数据）** | `sports_calendar.yaml`：赛事名、日期、`prepare_window_days: 30`、`peak_window_days: 7`、关键词（北马/全马/破3/配速）、内容角度（赛前清单/减量/比赛日穿搭/完赛恢复）、风险（不得用赛事 logo） |
| **怎么解（算法）** | ① 匹配时候选池 = 数据库热点 **+ 日历合成的"虚拟热点"**；② 新增 **E 分**（项目匹配 +60、品类匹配 +20、人群交集 +10、窗口期内 +10）；③ 权重改为 `0.28R+0.22T+0.16A+0.14P+0.10C+0.10E`；④ 硬门槛 `E<40 且 R<60 → 直接丢弃` |
| **怎么解（表达）** | 「赛事雷达」倒计时 + 卡片上直接写"赛前 4 周装备清单 / 赛前 2 周减量训练"这类节奏建议 |
| **可验证结果** | 北马 × 碳板跑鞋 = **87.0 分**（10 月就出卡，不用等新闻）；北马 × 瑜伽垫被 E 分门槛挡掉（不打"勉强蹭"的卡） |

一句话：**把"追热点"变成"排赛程"。**

### 9.3 问题三：内容写得不像运动圈、还容易踩线

| 环节 | 内容 |
|---|---|
| **原来的坑** | 通用禁用词只拦"最/第一/国家级"，拦不住体育特有的四类雷：**疗效宣称**（治好膝盖疼）、**成绩承诺**（包 PB / 快 2 秒）、**身份挪用**（国家队同款）、**赛事版权**（赛事 logo、赛道照片、运动员肖像） |
| **怎么解（合规）** | `sports_compliance.yaml`：forbidden_claims（治疗/康复/减重/提高成绩X秒/包完赛/专业级…）、required_disclaimers（护具不能替代医疗诊断、儿童须成人监护）、certifications（头盔 CE/EN1078/GB811）→ 生成时**硬拦截**，审核报告里写清"为什么不能这么写" |
| **怎么解（模板）** | 新增 3 个运动内容形式：**训练打卡 / 装备测评 / 赛事应援**；每个平台 skill 加一节"运动场景段落模板"（不新增平台，避免重写 5 份 skill） |
| **怎么解（事实校验）** | 沿用现有机制并扩展：正文里的尺码、重量、材质、认证编号必须能追溯到商品档案，**"提升 30%""快 2 秒"这类无来源数字直接标红** |
| **怎么解（人群）** | `sports_personas.yaml` 注入 pains/triggers/tone/avoid，自动分「新手版」（不甩行话）与「进阶版」（给对比、承认局限） |
| **可验证结果** | 小红书标题自动 ≤20 字、标签 ≤10 个；要求写"治好膝盖疼"→ 直接拒绝并给合规理由 |

一句话：**让 AI 只能说你数据里有的东西，说不了你不该说的话。**

### 9.4 问题四：商品档案不专业，后面的匹配和算账全部失真

| 环节 | 内容 |
|---|---|
| **原来的坑** | 通用商品档案只有"名称/品类/规格/卖点"，没有"运动项目、水平、尺码体系、发货重量、认证"——匹配不知道这鞋是跑鞋还是徒步鞋，算账不知道多重 |
| **怎么解** | 新增 `sport_profiles` 表（一行一个商品）+ 提取提示词增加运动维度 + `Product.tags` 增「运动项目/运动水平」两个维度（JSON 字段，不改表结构，老库不迁移不报错） |
| **为什么放新表** | `create_all()` 只建新表不加列，给已有表加列会 `no such column` —— 这也是现有 `product_costs` 的做法，本方案沿用 |
| **可验证结果** | 建档一次，后面匹配、内容、算账三处同时受益；`尺码矩阵批量导入`（同款多码=一个商品）列为 P2 可选 |

一句话：**领域数据先对了，后面的算法才有意义。**

### 9.5 问题五：一个商品在几个平台卖，口径打架

| 环节 | 内容 |
|---|---|
| **原来的坑** | 天猫佣金 6%、抖音佣金更高、得物还有鉴定费；同一款跑鞋按同一套口径算，等于没算 |
| **怎么解** | `promo_configs` 表本来就有 `platform` 字段 → 支持多套口径；新增"多平台对比算账"入口，一次输出三套账单并列 |
| **可验证结果** | 同一款鞋：天猫 / 抖音 两条账单并排，直接看哪边做活动还有利润 |

### 9.6 为什么这些机制"能work"（方法论，也是这个系统的底子）

1. **规则外置**：体育知识全在 YAML —— 换运动项目、换平台、换店铺不改代码，赛事日期变了改一行；
2. **AI 不产生数字**：金额、佣金、利润率全部由 `pricing.py` 纯函数算，模型只负责组织和表达 —— 这是它敢用在钱上的前提；
3. **硬门槛优先于调权重**：权重重排只让分数动 1~3 分，真正起作用的是"E 分太低直接丢"和"赛前 30 天进候选"；
4. **每个数字可追溯**：`profit_checks` 存入参快照与逐项拆解，`matches.subscores` 存 R/T/A/P/C/E 六项 —— 被问"这数字怎么来的"能现场点开；
5. **离线可演示**：赛事日历用本地 YAML，不依赖第三方接口限流，断网也能讲完整故事。

### 9.7 一张表看全：问题 → 机制 → 证据

| 商家的问题 | 靠什么机制 | 演示时能看到的证据 |
|---|---|---|
| 这套折扣到底赚不赚 | 重量运费 + 退货期望损失 + 组合装拆解 | 50.88（通用）vs 29.88（体育）→ 8.10% vs 4.76% |
| 这次赛事要不要跟、跟哪几款 | 赛事日历 + E 分 + 硬门槛 | 碳板跑鞋 87.0 分；瑜伽垫被门槛挡 |
| 文案会不会违规、像不像运动圈 | 合规词库 + 运动模板 + 事实校验 + 人群画像 | 违规词被拒；标题字数自动达标 |
| 商品档案专不专业 | `sport_profiles` + 运动标签 | 匹配/内容/算账三处同时可用 |
| 几个平台怎么定价不打架 | `promo_configs.platform` 多口径 | 两条账单并排对比 |

### 9.8 它**不**解决什么（避免过度承诺）

- 不做训练计划、运动康复建议、成绩预测（不是训练处方工具）；
- 不做经销商控价/价格监控（没有爬虫与监控能力）；
- 不承诺"内容一定过审"，只承诺"把风险标出来"；
- 不保证赛事信息实时准确（日历是运营知识，界面标注"以官方为准"）。

## 10. 用户使用逻辑全景：一个真实的运动装备店主怎么用

### 10.0 人物设定（后面所有场景都基于这个人）

> **李老板**，38 岁，"破风运动"店主，天猫 + 抖音双平台，约 60 个 SKU（跑鞋、羽毛球拍、护具、运动水壶）。
> 一个人管运营，会一点 Excel，**不看复杂报表**，一年踩两次大坑：一次是大促算错折扣亏了三万，一次是蹭赛事热点用了不合适的素材被限流。
> 他最常说的三句话：「这单到底赚不赚」「这周有什么能发」「别让我填太多东西」。

### 10.1 时间轴总览

| 时间点 | 他做的事 | 花多久 | 系统给他什么 |
|---|---|---|---|
| T0 装好当天 | 建档（粘贴 / Excel 导入） | 10–20 分钟（一次性） | 结构化商品 + 每款单件利润 + 缺项清单 |
| 每天 09:00 | 打开首页扫一眼 | 30 秒 | 「今日待办」：待审内容、待发布机会卡、亏损预警 |
| 每周一 | 看赛事雷达 | 3 分钟 | 未来 4 周赛事 → 匹配商品 → 内容排期建议 |
| 活动前 | 对话式算账 | 2–3 分钟 | 账单 + 逐项归因 + 方案 + 折扣上限 |
| 出素材时 | 生成 + 审核 | 每次 4–5 分钟 | 5 平台文案 + 合规/事实/字数校验 |
| 发布后 | 标记发布、复盘 | 1 分钟 | 内容与测算记录存档，月末可追溯 |
| 月末 | 翻利润记录 | 2 分钟 | 哪些活动真赚钱、哪些是在给平台打工 |

**一句话：他只动手三次（建档、每周一看雷达、活动前算一次账），其余都是系统主动递到眼前。**

### 10.2 六个阶段，逐个说清"他做什么 / 系统做什么"

#### 阶段 A｜第一次上手：把货"喂"进去（一次性，10–20 分钟）

- **他的动作**：把供应商发的商品资料丢进文本框，或者直接把 Excel 表格拖进「批量导入」。
- **他看到的**：一段大白话变成一张结构化卡片——名称、品类、规格、卖点、目标人群；**下面多了一块「运动属性」**（运动项目 / 适用水平 / 尺码体系 / 发货重量 / 认证 / 该品类退货率）。
- **系统在背后**：
  1. 提取提示词（扩展后的 `extraction.py`）识别"羽毛球拍、2U/3U、碳纤维、适合进阶"这些体育词；
  2. 从 `sports_taxonomy.yaml` 把品类归一（"碳板跑鞋"→`跑步/竞速鞋`）并挂上默认重量、退货率、认证要求；
  3. 立刻用 `pricing.py` 算出**单件利润与推荐售价**——建档完就看见钱；
  4. 列出**缺项清单**：「3 个商品缺发货重量（运费会算不准）」「1 个护具缺认证编号（内容有合规风险）」。
- **他得到什么**：60 个 SKU 的"利润底账"；以前这是三个晚上。
- **设计约束**：**不要求他懂体育术语**——没写运动项目就用品类默认值；没写重量就用品类均值并标注"估算值（建议核对）"。

#### 阶段 B｜每周一：看"赛事雷达"决定这周做什么（3 分钟）

- **他的动作**：点「热点看板 → 赛事雷达」，从上往下看未来 4 周。
- **他看到的**（这是特化后**唯一需要他主动"看"的页面**）：
  ```
  倒计时 26 天｜北京马拉松（10/31）  关联商品 3 款
    └ 机会卡：碳板跑鞋 · 综合 87.0（E 100）｜建议 10/10 发"赛前 4 周装备清单"
    └ 机会卡：能量胶 · 综合 74（E 80）｜建议 10/24 发"赛前一周减量怎么吃"
  倒计时 9 天｜城市羽毛球联赛（10/12） 关联商品 2 款
    └ 机会卡：羽毛球拍 · 综合 78（E 90）｜建议本周发"新手第一支拍怎么选"
  倒计时 41 天｜双十一预热（11/15）   关联商品 全店
  ```
- **系统在背后**：日历合成"虚拟热点"→ 程序算 R/T/A → E 分 + 硬门槛过滤 → 大模型只写"为什么适合 + 怎么拍"。
- **他得到什么**：**这周该发什么、哪款货、什么角度、什么时候发**。以前靠刷同行。
- **设计约束**：**低关联的卡宁可不出**——他不需要 20 条"看起来都能蹭"的建议，需要 3 条能落地的。

#### 阶段 C｜活动前：算清楚"这单赚不赚"（2–3 分钟）

- **他的动作**：在「利润防护」里选款，直接说人话："我打算上两件八折，再发 29 元券，卖 SR-72 会亏吗？"（也可以用内置的一句话模板，不用打字）。
- **他看到的**：
  - 左边对话：一句人话解释，不念公式；
  - 右边账单：成交额、买家运费、商品成本、**国内运费（按 2.3 kg 计费 36.00，通用口径是 15.00）**、平台佣金、利润 **−56.26**、毛利率 **−12.6%**，顶部红标「跌破 5% 红线」；
  - **优惠逐项归因**：不促销 / 只发券 / 只做两件折扣 / 叠加，四种情形利润并列——一眼看出是折扣杀的还是券杀的；
  - **可选调整**：5 张按利润从高到低排序的方案卡（"两件 95 折 + 29 券 → 利润 27.77"、"把价改到 280"…）；
  - **折扣上限**（新增）：按 8% 红线反推"最多只能打到 8.7 折 / 券最多 22 元"。
- **他得到什么**：不用打开 Excel 就能决定发不发；被追问"凭什么"能点开每个数字的来源。
- **设计约束**：**只读测算**——AI 不改价、不发券、不动店铺，避免"AI 把店搞坏"的恐惧。

#### 阶段 D｜出素材：生成 + 把关（每次 4–5 分钟）

- **他的动作**：从机会卡点「生成内容」，选平台（小红书/抖音/快手/B站/电商），点生成，然后看审核报告。
- **他看到的**：
  - 一份带标题、正文、标签、CTA 的稿子，**标题字数已卡在平台上限内**（小红书 20 字）；
  - **审核报告**：合规（是否疗效宣称/成绩承诺/身份挪用/赛事版权）、事实（尺码/重量/认证/价格是否与档案一致、有没有无来源数字）、平台（禁用词、标签数、emoji）；
  - **有问题就红字点名哪一句、为什么、怎么改**；他可以改完再审。
- **系统在背后**：`sports_compliance.yaml` + `risk_keywords.yaml` + 5 份 `platform_skill_*.md` 里的运动段落模板 + 事实校验（数字必须可追溯到档案）。
- **他得到什么**：一条能直接抄进后台的稿子，而不是"AI 味很重、还不敢发"的稿子。
- **设计约束**：**审核不通过不等于没收货**——对话里同时给"合规版改写"。

#### 阶段 E｜发布后与月末：只看结果（1–2 分钟）

- **他的动作**：发布后点「标记已发布」；偶尔打开「利润记录」和「审核记录」。
- **他看到什么**：每一条内容对应的是哪次测算、哪个热点、哪个口径；月末能回答"这个月哪场活动是真赚钱的"。
- **系统在背后**：`contents.status` 状态机 + `profit_checks` 存档 + `matches.subscores` 六项打分明细。
- **设计约束**：不做复杂 BI 图表——他只看"结论 + 一个数"。

#### 阶段 F｜设置：只在"口径变了"的时候进来（一年 3–4 次）

- **他的动作**：平台佣金涨了、快递涨价了、红线想从 5% 提到 8% → 改一处。
- **为什么重要**：**所有算账都以他为唯一事实来源**——改一次口径，全店测算立即跟着变，不用重算 60 个 SKU。

### 10.3 为什么这个顺序是"用户逻辑"而不是"功能逻辑"

| 功能逻辑（开发者视角） | 用户逻辑（李老板视角） |
|---|---|
| 先讲 5 个模块能干什么 | 先让我把货录进去，看见我赚多少 |
| 先讲匹配算法权重 | 先告诉我这周该发哪 3 条 |
| 先讲生成能力 | 先保证我发出去不会亏、不会被限流 |
| 荣誉感来自"技术先进" | 安全感来自"这单数字对得上" |

所以特化的第一原则是：**把钱放在最前面，把节奏放在第二，把创作放在第三。**

### 10.4 每个阶段的"失败兜底"（决定它是否敢被真实使用）

- 没配大模型 Key → 全流程用 Mock 可跑，界面上明确标注"规则模式"，不假装智能；
- 缺重量/缺退货率 → 用品类均值 + 标注"估算值"，账单里写"此数依赖估算，修正后自动重算"；
- 赛事日历没覆盖他的行业 → 明确写"当前覆盖跑步/羽毛球/健身/足球/篮球/冰雪，其他项目请在设置里补充"，而不是给个空页面；
- 审核规则误杀 → 每条拦截都能看到"命中哪条规则"，可一键反馈例外。

## 11. 创新点（在原方案之上新增）

### 11.0 什么算"创新点"（我的判定标准）

1. **别人没有**：通用电商 AI 工具（写文案/客服/数据看板）里没做成闭环的；
2. **有真实价值**：能直接改变商家的一个决定（发不发、发什么、什么时候发、打几折）；
3. **落地成本可控**：能在 P0/P1 工时内做完，不是画饼。

按这三条，我提 6 个创新点，其中 3 个建议进 P0（因为它们同时是演示爆点）。

### 11.1 I1｜赛事倒计时 → 自动内容排期表（"把蹭热点变成排产"）

- **创新在哪**：行业里的"热点工具"都是给一份**列表**（今天什么火）；这里是给一份**排期**——赛事前 4 周就已经排好了 4 条内容任务（装备清单 → 训练打卡 → 减量指南 → 完赛恢复），每条带建议发布日期、关联商品、内容形式。
- **怎么实现**：`sports_calendar.yaml` 里每个赛事配一个 `content_plan` 数组（偏移天数 + 内容形式 + 角度）；雷达页一键「生成排期」，直接写入 `contents` 表草稿（`status=draft`，带 `planned_date` 字段——新增列或复用 `audit_result` 里的元数据）。
- **演示效果**：点一下，屏幕上出现"未来 28 天的 4 张任务卡"，日期从今天算起。**这是最容易被记住的一屏。**

### 11.2 I2｜口径对照账：把"隐藏成本"摆上账单（"同一单，两种算法，差 21 块"）

- **创新在哪**：所有算账工具都只给**一个数**；这里给**两个数 + 差额**——通用口径 50.88 / 8.10%，体育口径 29.88 / 4.76%，中间一行红字「**固定运费口径高估了 21.00 元**」。
- **怎么实现**：`pricing.py` 的测算函数同时跑两套 `ShippingPolicy`（固定 vs 重量计费），返回 `variants` 数组；前端账单卡加一个切换开关。
- **为什么是创新**：它教育商家——"你以为的利润，和真实的利润，差在这里"。答辩时这一行字比任何功能列表都有说服力。

### 11.3 I3｜保本反推：从"我想赚 8%"倒推"最多打几折、最多发多少券"

- **创新在哪**：现有工具都是**正向**（给折扣算利润）；这里是**逆向**（给目标利润反解折扣上限）。商家真正的决策问题是"我能让多少"，而不是"如果我让了会怎样"。
- **怎么实现**：`pricing.py` 加纯函数 `max_discount_for_target(product, target_margin)`，对折扣率做二分求解（单调，10 次迭代内收敛），输出「最多 8.7 折 / 券上限 22 元 / 再让就跌破 8%」。
- **演示效果**：一句话给出"你的极限在哪"，而且能当场用正向测算验证一致（**自洽性即正确性证明**）。

### 11.4 I4｜赛事季活动体检：一键扫全店"哪些 SKU 在这个活动下会亏"

- **创新在哪**：从"单品算账"升级为"**活动级体检**"：输入一套活动参数（两件 8 折 + 29 券 + 赛事季），扫全店 60 个 SKU，按**亏损金额排序**输出——「SR-72 −56.26、J20 −41.30…共 4 款会亏，合计 −168.90」。
- **怎么实现**：复用现有 `store_scan` 工具 + `POST /agent/store-scan`，特化为"带活动参数的全店扫描"，返回按金额排序的列表与 3 条建议（改价/改券/不参与）。
- **演示效果**：**一屏红名单**。商家最怕的就是"活动一上，一半货在亏"，这个功能直接命中恐惧。

### 11.5 I5｜内容 ↔ 账单 ↔ 档案 三方一致性校验

- **创新在哪**：AI 生成内容的最大风险不是"写得不好"，是"**写的和你算的不一样**"——文案写"两件八折到手 269"，账单算出来是 447.80；文案写"仅重 180g"，档案里是 2.3kg。这里做**三方交叉校验**：正文里的每个数字，必须同时能在商品档案或测算记录里找到来源，否则标红。
- **怎么实现**：生成后跑一遍 `fact_check`：正则抓数字+单位、抓折扣/价格表述 → 与 `Product.specs` / 最近一次 `ProfitCheck.result` 比对 → 不一致进审核报告「事实冲突」分类。
- **为什么是差异化**：别人做"事实校验"只能查常识（有没有编造品牌），这里能查**自家数据**，因为账本就是它自己算的。

### 11.6 I6｜数字审计凭证：每个结论都能导出"这单是怎么算的"

- **创新在哪**：通用 AI 说"建议你卖 320"，你没法追问；这里每个数字都带**入参快照 + 公式 + 逐项拆解**，可导出成一张"测算凭证"（Markdown/图片），发给合伙人/会计对账，也可作为答辩材料。
- **怎么实现**：`profit_checks.inputs/result/explanation` 已经是结构化存档，加一个 `GET /products/{id}/cost/…` 之外的导出端点（或前端直接渲染成卡片截图），把 `pricing_policy.yaml` 的口径版本号一起打印。
- **价值**：把"AI 建议"变成"**可审计的计算**"——这是把钱交给 AI 试试的前提。

### 11.9 三个"答辩杀手锏"（按顺序讲，一条一个冲击点）

1. **"同一单，两种算法，差 21 块"**（I2）：先打"别人算的是假利润"，建立信任；
2. **"点一下，未来 4 周发什么已经排好了"**（I1）：再打"别人给列表，我们给计划"，展示差异化；
3. **"8.7 折是你的极限，再让就亏"**（I3）：最后打"我们不止告诉你结果，还告诉你边界"，收尾。

每一步都能当场用系统演示 + 用第二个功能自我验证（I3 的答案用正向测算复算，结果一致）——**可复算 = 可信**。
